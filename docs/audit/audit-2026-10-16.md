### CS-03 [low] useDebts.ts summary targets do not round reduction totals to cents
- **Evidence:** `src/hooks/useDebts.ts:40-42`,
  `const totalTarget = liveDebts.reduce((sum, d) => sum + d.totalAmount, 0);`
  `const remainingTarget = liveDebts.reduce((sum, d) => sum + (d.isSettled ? 0 : d.remainingAmount), 0);`
  `const paidTarget = Math.max(0, totalTarget - remainingTarget);`
- **Rule:** `AGENTS.md` (Non-negotiables)
- **Impact:** Iterative addition of floating-point numbers can produce IEEE 754 precision artifacts (e.g. `1000.0000000000001`). While UI presentation formats via `formatCurrencyAmount`, the unrounded numerical properties exposed in the `useDebts` hook return values can leak floating-point inaccuracies to consuming components or tests.
- **Fix:** Wrap the accumulated sums in `roundToCents()`:
  `const totalTarget = roundToCents(liveDebts.reduce((sum, d) => sum + d.totalAmount, 0));`
  `const remainingTarget = roundToCents(liveDebts.reduce((sum, d) => sum + (d.isSettled ? 0 : d.remainingAmount), 0));`
  `const paidTarget = roundToCents(Math.max(0, totalTarget - remainingTarget));`
  Gate tier: `src/context/`, `src/hooks/`, `src/lib/`.

### Supabase and the ledger

### SL-01 [medium] transfer_funds breaks replay on soft-deleted transactions and throws unique_violation
- **Evidence:** `supabase/migrations/20261006_phase93_transfer_funds_from_session.sql:80-86`,
  `if p_idempotency_key is not null then`
  `  select * into v_existing`
  `    from public.transactions`
  `   where user_id = v_user`
  `     and idempotency_key = p_idempotency_key`
  `     and is_deleted = false`
  `   limit 1;`
  and `supabase/migrations/20261006_phase93_transfer_funds_from_session.sql:175-185`,
  `when unique_violation then`
  `  select * into v_existing`
  `    from public.transactions`
  `   where user_id = v_user`
  `     and idempotency_key = p_idempotency_key`
  `     and is_deleted = false`
  `   limit 1;`
  `  if not found then`
  `    raise;`
  `  end if;`
- **Rule:** `docs/contexts/supabase-ledger.md:20`
- **Impact:** A retry carrying the key of a soft-deleted transfer skips the replay (the filter `is_deleted = false` breaks the replay rule), so the function tries the transfer again; the insert hits the non-partial `transactions_user_idempotency_uidx` (`supabase/migrations/20260901_baseline_schema.sql:151-153`), the handler's lookup with the same filter finds nothing, and `raise` returns a 23505 error. The block's balance updates roll back with it, so no money moves twice, but the caller gets an error instead of the replayed row that `record_transaction` would return.
- **Fix:** Remove `and is_deleted = false` and order by `order by is_deleted asc, created_at asc limit 1;` in both locations in `transfer_funds`, matching the implementation in `record_transaction` (`supabase/migrations/20260928_phase52_security_ledger.sql:244-249` and `supabase/migrations/20260928_phase52_security_ledger.sql:326-331`). Gate tier: `supabase/`.

### SL-02 [high] addTransaction omits unknown-outcome cloud refresh on transfer_funds failures
- **Evidence:** `src/context/FinanceContext.tsx:1848-1853`,
  `if (rpcError) throw isMissingRpcError(rpcError) ? new MissingLedgerFunction() : rpcError;`
  `const payload = rpcData as TransferFundsResult | null;`
  `// The RPC may already have moved the money: report it, never retry.`
  `if (!payload?.transaction) {`
  `  throw new Error('transfer_funds returned an unexpected response');`
  `}`
- **Rule:** `docs/contexts/supabase-ledger.md:18`
- **Impact:** In `src/context/FinanceContext.tsx:1828`, `rpcOutcomeUnknown` is initialized to `false`. While `record_transaction` (lines 1909, 1916) and `set_transaction_deleted` (lines 2173, 2178) flag `rpcOutcomeUnknown = true` if `isUnknownOutcomeError(rpcError)` or if `!payload?.transaction`, `transfer_funds` omits setting `rpcOutcomeUnknown`. If a network timeout, disconnect, or empty response occurs after `transfer_funds` commits on Postgres, `rpcOutcomeUnknown` remains `false`. In the `catch` block (`src/context/FinanceContext.tsx:1965-1978`), the client rolls back to `previousWallets` and does not call `refreshFromCloud()`, so the user is told the transfer failed while it committed, and the balances stay at their pre-transfer values until the next cloud reload. A user who re-enters the transfer in a new form (a new idempotency key) moves the money twice.
- **Fix:** Update lines 1848-1853 in `src/context/FinanceContext.tsx` to set `rpcOutcomeUnknown = true` when `isUnknownOutcomeError(rpcError)` or when `!payload?.transaction`, matching `record_transaction`. Gate tier: `src/context/`, `src/hooks/`, `src/lib/`.

### SL-03 [low] addTransaction assigns unrounded amount on guest transaction record
- **Evidence:** `src/context/FinanceContext.tsx:1937`,

- **Rule:** none
- **Impact:** In guest mode, `data.amount` is assigned directly to `newTx.amount` without `roundToCents(data.amount)`. In contrast, the wallet balance updates (`src/context/FinanceContext.tsx:1777`, `src/context/FinanceContext.tsx:1784`), `updateTransaction` (`src/context/FinanceContext.tsx:2241`), and the SQL ledger RPC (`round(p_amount, 2)`) all enforce 2-decimal cent rounding. - **Fix:** In `src/context/FinanceContext.tsx:1937`, wrap `data.amount` with `roundToCents(data.amount)`. Gate tier: `src/context/`, `src/hooks/`, `src/lib/`.
