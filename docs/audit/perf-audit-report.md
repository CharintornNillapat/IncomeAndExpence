# Performance & optimization audit — FinLife Tracker

**Status: frozen as of Phase 32 (2026-09-20).** Findings are write-once. Do not delete a finding when its task ships — append a `> Resolved by T<n>, commit <sha>` note under it instead. Every claim below carries a `path:line` citation, verified against the repository at commit `6c5d7df` (Phase 31's tip, the last `src/` change before this pass).

This is the second audit pass — the first (`audit-report.md`, frozen Phase 0) covered context re-renders, unmemoized computation, localStorage/sync, and dead code, and drove Phases 1–29. This pass covers what shipped since (Phases 30–31: category dedupe, Categories & Smart Rules hub, dashboard polish) plus a full re-sweep for correctness, render cost, dead code, and bundle weight that the first pass's scope didn't reach — most importantly, the write-path mutators in `FinanceContext.tsx`, which the first pass audited for *re-render* cost but not for *correctness* under optimistic-update failure.

Two findings turned out **larger** than initially scoped:

- **D11 — `src/hooks/useIdempotencyKey.ts:9-10` is a crash on insecure origins, not a style nit.** It calls bare `crypto.randomUUID()` inside a `useState` initializer, consumed by `TransactionForm.tsx:120` and `WalletTransferForm.tsx:81`. The Web Crypto `randomUUID` method is only exposed in a [secure context](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID) (HTTPS or `localhost`) — and `CLAUDE.md`'s own `npm run dev` command (`--host=0.0.0.0`) is written to be reached from a phone on the same LAN at `http://192.168.x.x:3000`, which is not a secure context. `crypto.randomUUID` is then `undefined`, the initializer throws, and there is no error boundary anywhere in `App.tsx` to catch it — the app white-screens. `FinanceContext.tsx:167-173` already has a guarded version with a `Date.now()+Math.random()` fallback; `useIdempotencyKey.ts` should call that, not reimplement a worse copy.
- **D12 — Deferring the shell modals is a bigger bundle win than the entry-chunk delta alone suggests.** `mathjs/number` (`vendor-math-D9WQvjt3.js`, 375.73 kB raw / **110.72 kB gzip**, unchanged since Phase 3/T7) is reachable eagerly *only* through `App.tsx`'s unconditional `QuickAddModal` → `TransactionForm` → `InlineMathInput` → `mathEvaluator` chain (`TransferFundsModal` → `WalletTransferForm` → `InlineMathInput` is the second path to the same chunk). Both are UI reachable only after a user taps a button. Removing them from the eager graph takes the single largest vendor chunk off the initial critical path — larger than any plausible entry-chunk-only optimization in this pass.

## A. Correctness (money-affecting) — new category this pass

The first audit pass scored `FinanceContext.tsx`'s mutators for re-render cost. It did not check what happens when their `await`ed Supabase calls fail, or whether their optimistic local writes and remote writes can desync. This pass does, because Phases 30–31 added a full write surface (Categories & Smart Rules hub) on top of the existing one without that check ever having been done.

- **`FinanceContext.tsx:1525-1575` (`setTransactionDeleted`) — cloud wallet balances silently stop updating on every soft-delete and restore.** `sourceNewBal`/`destNewBal` are declared `let ... = null` at `:1536-1537`, assigned **inside** the `setWallets` updater at `:1548`/`:1553`, and read synchronously at `:1566`/`:1570` to decide whether to fire the two `wallets` UPDATE calls. `setTransactions` at `:1532` already scheduled a state update earlier in the same function, so by the time `setWallets` is called, React is already processing an update for this component and does not take the synchronous first-call fast path that would run the updater function immediately — the updater runs later, during the commit React schedules, not before `:1566` executes. Both variables read back `null`. The two `if (sourceNewBal !== null)` / `if (destNewBal !== null ...)` guards at `:1566`/`:1570` are then always false, so **the wallet balance UPDATE calls never fire**. The transaction's own `is_deleted` UPDATE at `:1562-1565` does fire — so the row visibly flips (which is why no existing test catches this: every assertion in `soft-delete.spec.ts` checks the flag, never the balance) — but the wallet's cloud balance is left wherever it was, silently diverging from the correct local value from that point on. Every subsequent soft-delete/restore compounds the drift.
  - **Reference pattern that avoids this exact trap:** `addTransaction` (`FinanceContext.tsx:1256-1290`) resolves the wallets it needs **before** calling any `setState`, computes both new balances from that resolved snapshot, and only then calls `setWallets` with a plain, already-computed mapping. `setTransactionDeleted` needs the identical restructuring.
  - Scheduled: T63 (Phase 32).

- **9 mutators discard their Supabase call's result entirely — no error check, no rollback, no `MutationResult`.** Each does an optimistic local write, `await`s a Supabase call, and never inspects `{ error }`:
  - `updateWallet` (`:992-1011`), `deleteWallet` (`:1016`)
  - `updateCategory` (`:1110-1121`), `deleteCategory` (`:1145-1149`)
  - `deleteKeywordRule` (`:1204-1206`) — also a hard delete, see D2 above
  - `settleDebt` (`:1785-1790`), `deleteDebt` (`:1795-1800`)
  - `deleteDiaryEntry` (`:1878-1883`)
  - `setTransactionDeleted` (`:1532-1574`, same function as the desync bug above)

  `addTransaction` is the **only** mutator in the file with a full rollback: local restore (`:1479-1481`) plus remote compensation of whatever had already committed (`:1486-1507`). `CLAUDE.md`'s own Validation & MutationResult convention says "Mutating context methods return `MutationResult`... rather than throwing or failing silently" and "Surface Supabase errors too — do not swallow them" — these 9 mutators currently do exactly the swallowing that rule prohibits. A rejected write (offline, RLS failure, expired session) leaves local state permanently ahead of cloud state with no user-visible failure, worst on `setTransactionDeleted` because it moves money.
  - Scheduled: T65 (wallets/debts), T66 (categories/diary/keyword rules), both following `addTransaction`'s pattern (Phase 33).

- **`addTransaction`'s rollback can discard a mid-flight realtime reload.** `FinanceContext.tsx:1270-1272` snapshots `previousWallets`/`previousDebts`/`previousTransactions` from the ref mirrors before awaiting up to 4 sequential round-trips (`:1389-1445`). If the realtime subscription (`:861-895`) lands a reload from another device in that window, it repoints the refs to server truth — but the catch block's rollback (`:1479-1481`) restores the *pre-fetch* snapshot regardless, silently overwriting the newer server state with stale local state. Low-frequency (needs a concurrent second client plus a write failure), but a real data-loss path once cross-device sync is in active use.
  - Scheduled: T69 (Phase 33) — lowest priority in that phase; needs a revision counter, not just a ref-identity check, since `addTransaction` writes optimistically before the ref could differ for any other reason.

## C. Render cost

- **`AnimatedCounter.tsx:19-29` — the largest single runtime cost in the app.** `animate()`'s `onUpdate` calls `setDisplayValue` on every animation-frame tick (`~60`/s over a `duration: 1.2`s spring-eased animation ≈ 72 React state updates per instance per animation). It is mounted once per wallet card (`WalletAccountsGrid.tsx:124`, `WalletsView.tsx:132`), 3× in `CashflowMetricsCards.tsx:37,69,116`, once in `TotalWealthHero.tsx:43`, and once, always-mounted, in `NavbarLedgerStatus.tsx:68`. Any ledger write that changes a displayed total restarts every one of these simultaneously — on a dashboard with 4 wallets that's 6 counters × ~72 renders each in under 1.3 seconds. `baseline-metrics.md`'s existing S1/S2 Profiler harness already measured this component at **590 renders (S1, cold load)** and **636 renders (S2, one write)** — by far the largest number in that table, an order of magnitude above every other component measured. Scheduled: T70 (Phase 34), fixed by moving the frame-by-frame write from `setState` to a direct `ref.current.textContent` write, so the animation is visually identical but produces zero React renders.
- **`useTransactions.ts:42-50,107-119` — a wallet *balance* change re-filters the entire ledger.** `filteredTransactions`'s memo depends on `walletNameMap`/`categoryNameMap`, which are themselves memoized on the whole `wallets`/`categories` arrays (`:42-50`) even though only each item's `.name` is ever read from them. A wallet's balance changing produces a new `wallets` array reference (any `setWallets` call does, including the one inside `addTransaction`), which invalidates `walletNameMap`, which invalidates `filteredTransactions`, which re-runs every filter predicate over the full transaction list — for a change that has nothing to do with which transactions match. Scheduled: T71 (Phase 35).
- **`DashboardView.tsx:173-190,205` — the same category lookup map built twice per invalidation.** `categoryBreakdown` calls `buildLookupMap(categories)` at `:174`; a second, separate `categoryMap` is built from the identical `categories` array at `:205` for a different consumer in the same component. Scheduled: T72 (Phase 35), which also replaces `:193-201`'s full `.sort()` (to select a top-5 slice) with a single linear top-5 pass.
- **`DebtsView.tsx:43-49` (`handleDelete`) — the one place an unmemoized prop genuinely defeats a real memo.** Its `useCallback` deps are `[debts]`, and it is passed to `DebtCardItem` (`src/components/DebtCardItem.tsx:15`, which **is** `React.memo`'d) inside a `.map()`. Every debt-array change gives `handleDelete` a new identity, which invalidates every card's memo simultaneously, regardless of which debt actually changed. Distinguish this from the four D1 sites above — this is the one case in the whole sweep where the child is actually memoized. Scheduled: T73 (Phase 35).
- **`TransactionsView.tsx:502-527` — CSV dry-run preview renders every parsed row unbounded.** A large import (thousands of rows) renders that many `<tr>`s, each running `formatCurrencyAmount`, inside a `max-h-60` scroller that shows perhaps a dozen at a time. The summary counts above it (`:475-485`) already total the whole file. Scheduled: T74 (Phase 35), capped at 100 rows with a "+N more" footer.
- **`AuthModal`/`ReloadPrompt` are unmemoized children of `MainApp`, so they re-render on every `MainApp` render regardless of their own (stable/absent) props.** Already recorded in `baseline-metrics.md`'s Findings section from the Phase-4 Profiler run, never turned into a task. Neither subscribes to finance context, so `CLAUDE.md`'s memo-a-subscriber rule doesn't block it. Optional, lowest priority (T75, cut-first if Phase 35 runs long).

## D. Bundle weight

- **`App.tsx:236,253,256,261` mount `AuthModal`, `QuickAddModal`, `TransferFundsModal`, `AddWalletModal` unconditionally**, all four eagerly imported (`:8-11`). `isOpen` is a prop consumed only inside the shared `Modal` primitive (`Modal.tsx:77-78`), which gates the *children*, not the wrapper — so each wrapper's own hooks (`QuickAddModal.tsx:21-22`'s `useFinanceState()`/`useFinanceActions()`, `TransferFundsModal.tsx:28`'s `useWallets()`) run at app start whether or not the modal has ever been opened. This drags `TransactionForm` (458 lines), `InlineMathInput` (263 lines) plus `mathEvaluator`/`mathjs`, `AuthModal` (276 lines) plus `zod`, `AddWalletForm` (177 lines), and `WalletTransferForm` (226 lines) into the eager entry graph for UI that is, by definition, unreachable until a user taps a button. See D12 above for why the `mathjs` piece specifically is the headline number. Scheduled: T76 (Phase 36) — see that task's note on why a bare `React.lazy` swap is insufficient and would in fact break the app (no `<Suspense>` boundary currently covers `App.tsx:236-261`, and unmounting on `isOpen: false` would cut short `Modal`'s exit animation and `TransferFundsModal`'s delayed-close success flash).
- **`DiaryView.tsx:22` imports `exportDiaryToJson` from `csvExchange.ts`, dragging `papaparse` into DiaryView's lazy chunk for a function that never uses it.** `exportDiaryToJson` (`csvExchange.ts:39-70`) builds a JSON `Blob` directly; `Papa` is only used by the CSV import/export functions in the same file, which `DiaryView` never calls. Scheduled: T77 (Phase 36) — move the one function to its own module.
- **`FinanceContext.tsx` is 2,025 lines and 100% eager** (imported from `App.tsx` via `FinanceProvider`), the largest file in `src/` by a wide margin. Not scheduled as a task this pass — splitting a stateful context provider by domain is a structural change with its own risk profile, and every mutator inside it is already load-bearing for Phase 33's correctness work landing first. Flagged here for a future pass, not for this one.
